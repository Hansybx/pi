# 为 pi 做贡献

本指南的存在是为了给双方省时间。

## 理念

先说最重要的事：**pi 的核心是极简的**。

如果你的功能不属于核心，它就应该做成扩展。让核心臃肿的 PR 很可能会被拒绝。

Pi 的核心之所以存在，是为了保持极简并且可扩展，从而能被扩展所影响和操控。不过，即便为扩展预留的 hook 点，也应经过充分考量和讨论，以避免加入不可维护的臃肿和复杂的交互。

## 唯一规则

**你必须理解你的代码。** 如果你无法解释你的改动做了什么、它如何与系统其余部分交互，你的 PR 会被关闭。

用 AI 写代码没问题。提交自己并不理解的 AI 生成垃圾则不行。

如果你使用 agent，请从 `pi` 根目录运行它，这样它能自动读到 `AGENTS.md`。你的 agent 必须遵守该文件中的规则和准则。

## 贡献门槛

来自新贡献者的所有 issue 和 PR 默认自动关闭。

周五到周日提交的 issue 不保证会被评审。如果有紧急事项，请在 Discord 上询问：https://discord.com/invite/3cU7Bz4UPx

维护者每天评审自动关闭的 issue，并重新打开有价值的那些。不符合下方质量标准的 issue 不会被重新打开，也不会收到回复。

批准通过维护者在 issue 上的回复完成：

- `lgtmi`：你未来的 issue 不会被自动关闭
- `lgtm`：你未来的 issue 和 PR 不会被自动关闭

该命令必须位于回复开头（可以在一个或多个 `@username` 提及之后）或结尾。`lgtmi` 不授予提交 PR 的权利。只有 `lgtm` 授予提交 PR 的权利。

## Issue 的质量标准

如果你开 issue，必须使用两个 GitHub issue 模板之一。

如果你开 issue，请保持简短、具体、值得一读。

- 保持凝练。如果一屏放不下，就太长了。
- 用你自己的语气写（不要用 LLM 生成文本；如果必须用，随后补一条明确标注 AI 的评论）。
- 清楚陈述 bug 或请求。
- 解释它为什么重要。
- 如果你想自己实现这个改动，请说明。

如果 issue 是真实的且写得好，维护者可能会重新打开它，或按上述命令位置回复 `lgtmi` 或 `lgtm`。

## 封禁

如果你两次无视本文档，或者用 agent 生成的 issue 刷爆 tracker，你的 GitHub 账号会被永久封禁。

如果你通过自动化提交大量 issue，你的 GitHub 账号会被永久封禁。没有反悔的余地。

## 提交 PR 之前

除非你已经通过维护者在上述命令位置使用 `lgtm` 获得批准，否则不要开 PR。

提交 PR 之前：

```bash
npm run check
./test.sh
```

两者都必须通过。

不要编辑 `CHANGELOG.md`。变更日志条目由维护者添加。

如果你要为 `packages/ai` 添加新的 provider，所需测试见 `AGENTS.md`。

## FAQ

### 为什么新 issue 和 PR 会被自动关闭？

pi 收到的 issue 数量超过维护者能实时、负责任地评审的量。许多报告达不到本指南中的质量标准，或没有遵循 CONTRIBUTING.md。有些是通过 agent 不加思考丢到仓库的，而不是由提交者自己审阅和打磨。自动关闭创造了一个缓冲，让维护者能按自己的节奏评审 tracker，并重新打开达到质量标准的 issue。

### 为什么周末的 issue 优先级更低？

我们在工作时间内分拣 tracker。这意味着周末可能堆积更多 issue。周五到周日提交的任何内容都可能在周一的评审队列中被漏掉或降低优先级。如果问题紧急，请在 Discord 上提问，并附上简短版本、复现步骤和相关日志。

### 为什么有些 issue 得不到回复？

回复也是维护工作。低信号 issue、表述不清的报告、重复项以及不遵循本指南的 issue 可能不经讨论就被关闭。这样能为可复现的 bug、经过思考的请求，以及那些已经把报告做到可供行动的贡献者留出时间。

### 为什么不让 AI 分拣一切？

AI 可以帮助归类重复项、总结报告、发现缺失信息。但它不被信任来做维护者的最终决定。打磨过的 AI 生成 issue 仍可能是错的、有误导性的，或调查代价高昂。人类评审仍是最后一道关。

### 这是对贡献者有敌意吗？

不。这是防止倦怠和 tracker 垃圾的护栏。简短、具体、可复现的 issue 是受欢迎的。经过思考的贡献是受欢迎的。自动化的垃圾、理所当然的态度，以及大量低投入的报告不受欢迎。

## 我在哪里可以了解计划？

Earendil 使用 RFC 讨论较大的变更。并非所有 RFC 都是公开的，但相当一部分是。它们可以在 [rfc.earendil.com](https://rfc.earendil.com/keyword/pi) 找到。
