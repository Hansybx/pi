# 安全地运行 Pi

把模型生成的命令和代码视为不可信内容。Pi 能以启动它的账号权限读取、修改并执行文件，并且它不会在每次工具调用前都请求批准。除非操作系统或虚拟化边界加以限制，扩展、包安装器、语言服务器以及其他子进程都以同样的权限运行。

文件、注释、指令、命令输出和模型响应都可能通过提示词注入影响模型。项目信任控制启动时加载哪些项目资源，但它不会让这些内容或由此产生的操作变得安全。

当生成的操作有误或带有恶意时，安全来自限制 Pi 能够访问和影响的文件、凭证、进程与网络服务。观察对话记录、使用项目信任以及审阅变更都不会构成安全边界。

## 选择运行 Pi 的方式

不同的 Pi 运行方式对生成的命令可访问的内容设置了不同的限制：

| Pi 的运行方式 | 仍受保护的内容 |
|---|---|
| 直接运行，使用其操作系统用户的权限 | 该用户无法访问的任何内容。专用用户账号可以收窄这些权限，但 Pi 仍与其他用户共享操作系统和网络。 |
| 完全运行在容器、虚拟机或沙箱内 | 你未向该环境暴露的宿主机文件和进程。如果你在其中提供凭证和网络服务，它们仍然可访问。这通常是实际可行的最强选项。 |
| 在隔离环境之外运行，只有内置工具在隔离环境内运行 | 通过那些工具执行的操作无法触及宿主机资源。Pi 本身和其他扩展仍处于边界之外，因此这是一种范围更窄的隔离形式。 |

工作文件夹控制资源发现和工具的默认位置，但它不能阻止命令访问 Pi 进程可用的其他路径。

无论选择哪种方式，都只提供任务所需的文件和服务。尽可能把凭证留在该环境之外，或使用范围窄、有效期短的凭证。当命令不需要网络访问时，限制网络访问。

有关各种隔离方式的配置说明和限制，请参阅[在隔离环境中运行 Pi](containerization.md)。

## 理解项目信任

项目信任控制 Pi 是否加载工作文件夹提供的大部分设置和资源。它防止某个文件夹在你批准之前静默加载可执行扩展。

项目信任不是完整的启动边界。Pi 在选择或创建会话时会读取项目的 `sessionDir` 设置，这发生在它确定项目信任之前。拒绝信任会阻止其余项目设置和受保护资源加载，但无法撤销最初那次会话目录查找。

项目信任不会限制工具调用可以访问或影响的内容。Pi 启动后，已启用的工具仍使用 Pi 进程的操作系统权限。文件夹中的指令和其他内容也可能影响模型。

### 受项目信任保护的资源

当 Pi 从当前工作目录发现以下任一资源时，它要求做出项目信任决定：

- `.pi/settings.json`
- `.pi/mcp.json`
- `.pi/extensions`、`.pi/skills`、`.pi/prompts` 或 `.pi/themes`
- `.pi/SYSTEM.md` 或 `.pi/APPEND_SYSTEM.md`
- 当前目录或祖先目录中的项目 `.agents/skills`

只有空的 `.pi` 目录不需要项目信任。

授予项目信任允许 Pi 加载：

- 项目设置
- 来自 `.pi/mcp.json` 的项目 MCP 服务器
- `.pi` 下的扩展、技能、提示模板、主题和系统提示词文件
- 通过项目设置配置但缺失的包
- 项目本地扩展和项目包扩展

拒绝项目信任会跳过这些受保护资源，但上文所述的初始 `sessionDir` 查找除外。

无论项目信任如何，`AGENTS.override.md`、`AGENTS.md` 和 `CLAUDE.md` 等上下文文件都会加载，除非你禁用上下文加载。即使你拒绝项目信任，也要把文件夹中的指令视为不可信输入。

### Pi 如何做出信任决定

命令行 `--approve` 或 `--no-approve` 覆盖项优先生效。当存在受保护资源且没有命令行覆盖项时：

1. 用户级和命令行扩展可以处理 `project_trust` 事件。第一个返回是或否的扩展拥有该决定。
2. 如果没有扩展作出决定，Pi 会查找针对当前目录或其某个父目录已保存的决定。最接近的决定生效。
3. 如果没有适用的已保存决定，Pi 遵循全局 `defaultProjectTrust` 设置，其默认值为 `"ask"`。

已保存的决定使用规范目录路径，存放于：

```text
~/.pi/agent/trust.json
```

使用 `/trust` 为将来的 Pi 进程保存决定。

### 没有交互式提示时的项目信任

print 模式、JSON 模式和 RPC 模式无法显示内置的信任提示。如果没有适用的命令行覆盖项、扩展或已保存决定：

- `defaultProjectTrust: "always"` 会加载受保护的项目资源。
- `defaultProjectTrust: "ask"` 或 `"never"` 会跳过它们。

当自动化运行需要明确的一次性决定时，使用 `--approve` 或 `--no-approve`。

## 降低影响并改善恢复

这些做法不能替代隔离，但它们可以减少暴露或让恢复更容易：

- 只给 Pi 授予任务所需的文件和服务。
- 在重大变更前使用快照、备份或版本控制。
- 在加载扩展和包之前先审阅它们。扩展在 Pi 进程内执行。
- 优先使用范围窄、有效期短的凭证。
- 在把结果应用到另一个系统之前，审阅 diff 和生成的输出。
- 在导出或分享会话之前先审阅它们。它们可能包含对话期间暴露的提示词、工具参数、命令输出、文件内容和凭证。

## 报告安全问题

遵循仓库的[安全策略](https://github.com/earendil-works/pi/blob/main/SECURITY.md)。不要为安全敏感的报告提交公开 issue。

本地 agent 的预期行为、来自不可信内容的提示词注入、缺少内置沙箱，以及用户安装的扩展或技能的行为，通常都在安全边界之外，除非报告能证明存在权限边界绕过或本地用户原本不具备的访问能力。
